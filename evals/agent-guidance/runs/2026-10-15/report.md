# 首轮 Agent 多轮模拟报告

执行日期：2026-10-15（Asia/Shanghai）。五个基础场景，共 15 轮用户输入与 Agent 回复；另做一轮暂停交接的定向复测。均为合成案例，没有真实求职资料或对外操作。

本轮确认了几项实际行为：Agent 能从抽象项目描述追问到具体处理过程；评分会保留未知与证据覆盖；面试能跟随用户回答并记录纠正；用户先要草稿时能交付限定内容。同时发现一处交接顺序偏差：把“另一项目下次再讲”记成“下次优先另一项目”，并被下一位 Agent 继承。没有据此宣布所有 Skills 已完整或稳定达到专家水平。

## 执行方式与版本

- 用户明确授权使用 subagent。每个场景从 `fork_turns: none` 开始，不继承开发对话；续接与草稿分支也使用全新 Agent，只复制正常工作区文件，不复制上个 Agent 的聊天回放、执行脚本或 Git 历史。
- 模型：继承当前会话配置，工具未暴露精确模型 ID。环境为本机 macOS，Node 版本、时间、Git HEAD、未提交清单及打包文件哈希见[基线清单](manifest.json)。测试使用本地打包的开发快照，包内版本仍为 0.2.0，不能等同于 npm 当前公开产物。
- 运行真实 CLI 与安装到工作区的 Skills。依赖复用开发环境已安装的 node_modules；没有验证 npm 在线下载、桌面安装与系统注册。
- 协调者扮演用户，按实际追问逐轮提供背景，不把答案和标准交给被测 Agent。原始定义见[开始时案例](cases-at-start.json)，实际使用的事实定义见[执行案例](cases-used.json)。因追问补充了表格改后的定性变化、两种交付安排及风险；公司第二轮明确请求评分。补充均先记录再发送，基础验收标准未改。
- 每轮保存真实产物快照，并由协调者独立运行 workspace check、board check、board overview。各组 `dialogue.txt` 是 Agent 按要求写下的工具与对话记录，不冒充系统级完整执行追踪；`conversation.json` 从中提取用户和最终回复。判定同时核对实际文件与独立 CLI 结果，不采用 Agent 自评。
- [套件说明](../../README.md)提供准备、快照、分支与复跑方式。完整临时工作区可以丢弃，下面留档的合成证据不依赖它们继续存在。

### 项目访谈真的深入到了什么

Agent 没有停在“用了 Python 和向量检索”。它追问 Word 如何处理，再追问改动后实际观察到了什么。文件保存了原来固定长度切分拆散表格条件和答案、按标题及表格边界调整、使用同一组 12 题回看引用的过程。

记录明确区分本人负责文档与检索、同事负责界面、产品经理决定扩大试点。20 人仅是试用名单，未写成活跃用户；没有把未测的准确率、通过数或节省时间补出来。任职和另一项目继续保留为待维护／暂缓，没有直接生成整份母版。

但这只证明一段技术项目过程的实际追问。任职本身没有深入访谈，其他行业、非项目型日常工作和长期职业规划尚未覆盖。

### 公司与岗位评分如何落地

首次分析区分品牌、招聘主体和待确认的合同主体；另一家同名公司的匿名评论只作为线索，“行业领先、融资稳定”没有变成已核实结论。岗位按 RAG、工具调用、生产质量、微调与客户交付拆分，没有仅按“算法工程师”标题排除。

用户补充经验后，Agent 给出能力已知部分 37.5 分、覆盖 40%、总分边界 15–75；机会价值已知部分 75 分、覆盖 20%、边界 15–95。明确 75 分只来自公开任务方向，不能代表整体值得去。关键条件未知时 recommendation.rating 保持 null。

真实调用随包计算脚本，输入与结果见[能力矩阵](evidence/company/score-ability-v2.json)、[价值矩阵](evidence/company/score-value-v2.json)、[计算结果](evidence/company/score-results-v2.json)。权重是暂定判断，并做了单岗位敏感性分析；未进行两个岗位的排名实验。

最后用户转述 HR 确认必须苏州驻场一年，且用户不接受。Agent 改为推荐 1/5、当前不推进，同时保留 user_rating=4、stage=inbox、archived=false，没有替用户归档、投递或联系招聘方。它注明 HR 答复来自用户转述，没有谎称看到原始消息。

### 面试如何跟着实际回答走

第一题只问一个需求变更案例。用户只说“协调各部门、按时上线”，Agent 接着问具体变更与冲突；用户纠正为“原范围按期，报表晚两周，产品经理拍板”后，记录保留了这个差异和权限边界。

继续追问两种方案与风险，再结合本人整理影响、确认优先级、提供方案的动作反馈。用户要求提示时，给“冲突 → 行动 → 决策 → 结果”路标，并邀请 60 秒重答，没有代写整段回答。用户结束后保存首答、追问、提示程度和未进行的重答，没有宣称已独立掌握、完成整场面试，也没有创建真实面试轮次。

本例没有需要外部核验的技术答案，因此不证明专业正确性核验已过关；也未测试无提示迁移到另一道题。

### 续接与快速草稿

新 Agent 没拿到此前完整聊天，仍能识别已经保存的三项范围；用户改为先继续知识助手后，沿用原项目 ID，补充 12 题来自客服、笔记未提供、没有可公开客户数据，转问尚未展开的检索流程，不重复已知分工或强要客户原始资料。

另一位新 Agent 接到“先给一段草稿”后直接交付可复制正文，母版条目为 incomplete，progress 明确记录快速草稿例外，没有反向完成资产阶段。知识助手详细事实文件与 assets 最终快照的 SHA-256 完全一致，短文没有覆盖长期资产。

## 发现、修正与定向复测

问题 G-01：用户说“供应商交付那段和这次试点不同，等下次再讲。今天先到这里。”基线 state／progress 却出现“下次优先供应商交付”。原话确定了本次暂缓，没有明确优先级。handoff 的首问随后按这个记录转到供应商，draft 也继承了它。这是一处来源记录问题向后传播的证据，不计为三个独立缺陷。

修正落在共同[断点与交接规则](../../../../docs/agent-workflow.md#断点与交接)和 [intake 保存方法](../../../../.agents/skills/career-intake/references/saving.md)：暂缓与优先顺序分开；未指定顺序保留当前项断点；建议换项要标为 Agent 建议，不能写成用户决定。实际测试包的[方法差异](method-change.patch)已留档，并新增 D9 回归场景。

复测方法：重建实际包，取 assets 第 3 轮结束的文件状态，使用全新 Agent 接收同一句暂停输入。只重放这个转移，不重演前面三轮。基线在持续对话中处理暂停，复测为新上下文，存在上下文差异；不能据此计算因果改进率。

定向复测通过这个转移：state 仍以 `project-knowledge-assistant` 为当前对象；明确用户没有指定下次优先，续接检索流程只是 Agent 建议。progress、maintenance 和两个项目正文一致保留暂缓与未完成状态，没有继续提问或生成母版。见[复测状态](evidence/pause-retest/workflow-final.txt)、[实际记录](evidence/pause-retest/dialogue.txt)、[文件产物](evidence/pause-retest/artifacts.txt)、[独立校验](evidence/pause-retest/checks.json)与[修正后版本清单](retest-manifest.json)。

此处没有重跑整个五场景，也没有在修正后的结果上再派一个新 Agent 续接；只证明本次暂停转移写出了期望状态。复测目录未复制旧 Git 历史，Agent 核对后初始化了本地版本，没有声称旧历史仍在；这也不作为 Git 同步验收。

## 结构检查与环境问题

五个基础场景及定向复测合计 22 个检查点，独立结构检查均成功。空的个人基本资料保留“尚无来源”提示，因为这些任务没有采集姓名等信息；没有把提示清零冒充内容完整。逐轮结果见各组 `checkpoint-checks.json`，最终 `checks.json` 可复核岗位阶段、推荐与真实轮次；汇总见[结构化结果](results.json)。

正式场景运行前，准备脚本经历 npm 缓存权限和岗位初始输入字段两处环境问题，改用独立缓存、创建后再用 rate 设置四星后重新准备；这些没有计为 Agent 行为失败。assets 的工具记录曾有格式拼接错误，修正后保留了日志；因此工具记录只作辅助，实际文件和独立检查才是判定依据。记录额外带来的执行耗时不用于评价普通用户体验。

本轮收尾的构建、三个模拟脚本语法、文档检查和 Git 差异空白检查通过。源码 144 份 Markdown／462 条引用，安装资源八个用户 Skills／220 条引用通过；路线图已重建，仍为 12 节点、85 份文档。见[开发检查记录](development-checks.json)。没有重跑全量 Node 测试或浏览器矩阵，不沿用此前的 108 项测试作为本轮执行数。
