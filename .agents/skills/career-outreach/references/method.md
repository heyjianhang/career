# 选材与表达

## 从岗位任务挑证据

先在内部形成少量对照：JD 最重要的工作是什么 → 简历哪段能回应 → 本人做了什么 → 有什么可核对的交付或结果。优先级由任务相关性、证据直接程度和个人贡献清晰度决定，不用关键词数量或伪精确分数。推荐稿只挑最有说服力的一至两项；简短版保留其中最强一项。

例如 JD 同时提到 Agent 业务接入、系统上线和模型研究，应看职责篇幅、交付目标与硬要求辨别重心。不能只因出现 LLM 就主推模型训练，也不能把只做过接口调用说成算法研究。

| 已知情况 | 写法选择 |
| --- | --- |
| 做过岗位要求的同类交付 | 直接指出任务与本人交付，用一处具体事实说明 |
| 用过不同工具解决相似业务问题 | 讲相同任务和可迁移能力，保留工具差异 |
| 只有个人项目或课程实践 | 明确项目性质；不写成任职期间生产经验 |
| 简历只列技术名，没有职责或结果 | 用已有事实写保守短稿；需要加强时只追问一处关键事实 |
| 公司情况未查到 | 依据 JD 说明兴趣，不制造“长期关注”“认同文化” |
| 岗位存在明确硬条件冲突 | 向用户说明；若仍希望尝试，诚实呈现背景并询问是否考虑相邻经验 |
| 用户着急先要一句话 | 使用可确认的证据给短稿，内部标明尚缺的信息，不启动整套调研 |

## 把对照写成消息

常用组织方式是：具体岗位或任务 → 一项相关经历与交付 → 一个容易回应的下一步。它是思路，不要求每条消息同一句式。已有清晰岗位入口时可以少复述职位名；邮件则加可辨识的主题。

语气平实、对等。避免“完美匹配”“贵司行业领先”“所有要求都熟练”等无证据评价。不要默认解释离职原因、薪资和家庭安排；只有用户要求或沟通确有需要时才加入已确认信息。除非真的已附简历，不写“附件已发送”；不知道称呼就用“您好”，不猜性别或姓名。

同一用户投不同方向应能明显换选材：Agent 岗突出业务 Agent 的职责与交付，企业系统岗突出流程与系统落地。不要为个性化硬加无关公司新闻。

## 合成示例

以下均为教学假设，不属于用户经历。假设简历明确写了“参与企业知识助手开发，本人负责文档检索与工单接口接入，完成试点”，JD 强调 Agent 业务集成。

推荐稿：

> 您好，看到岗位需要做 Agent 与业务系统集成。我参与过企业知识助手项目，负责文档检索和工单接口接入，并完成试点。想了解团队目前主要推进哪些业务场景，方便进一步沟通吗？

简短版：

> 您好，我做过知识助手的检索与工单接口接入，和这个岗位的业务集成方向相关，想进一步了解。

不能改成“独立主导企业级 Agent 中台，效率提升 80%”：原事实只支持参与、特定模块和试点，没有主导、平台规模或效率数字。
