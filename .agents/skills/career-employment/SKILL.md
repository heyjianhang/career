# 任职资产：理解这段工作，而不只列职位

目标是留下一个人如何在具体组织环境里工作的完整记录。先读 [资产写作方法](../../../docs/career-assets.md) 与 [推进规则](../../../docs/agent-workflow.md)。本 Skill 处理用户过去或当前的任职；求职目标公司的外部研究由 career-board 负责，不能拿今天的公司网页推断用户任职时的组织情况。

## 接手与首份记录

沿 [intake 启动方法](../career-intake/references/startup.md) 检查工作区，按 AGENTS 选择桌面或 npm 入口。读 `context/progress.md`、`context/state.md`、当前维护项和已有任职／项目来源。先判断是新任职、原任职的新阶段还是事实纠正。

从已有材料提取可确定内容，使用 [任职模板](../career-intake/templates/facts/employment.md) 建立 `resume/facts/employment/<employment-id>.md`，不要等完整才保存。雇主、客户、派驻单位与任职性质分别核对；未知用 null，不自造公司关系、职位或日期。

## 深入顺序

按 [任职访谈方法](references/deep-interview.md) 判断下一问。通常先知道任职时的组织与业务、本人角色和阶段，再列出主要工作线，然后逐项展开关键过程。已有材料回答了哪一部分就直接保存，不重问。

用户谈到具体项目时，按 [career-project](../career-project/SKILL.md) 深入项目，并通过 employment_id 关联；切换的是方法，不是另开 Agent 或要求用户重新介绍。项目正文详细记录实现过程，任职正文保留职责地图、组织语境、跨项目工作与项目链接，避免复制两份完整故事。

一轮通常一个主问题。明确告诉用户会先把这段经历记录详细，简历之后再提炼。先保存确定内容，再问角色、取舍、行动与结果的缺口，不急于推荐职位或进入排版。

## 整理深度与写法

任职正文需让接手者知道：当时组织在做什么、用户处于哪里、实际负责哪些工作、能作哪些决定、与谁协同、职责如何变化、有哪些可展开的实际事件。区别日常职责、个人行动与团队成果。业务背景只记录与理解工作有关的部分，不要求披露全部内部资料。

按模板核心章节组织，可增加阶段与职责线三级标题。无独立项目的日常运营、支持、行政等工作，同样在任职正文记录具体流程与事件，不强行包装成项目。失误、改进与未完成事项可以作为复盘资产，但不写成已取得的成就。

来源、事实、问题、维护清单按 [落盘步骤](../career-intake/references/saving.md) 保存，重复补充沿用 ID。晋升或职责变化先保留时间线；确实是独立任职阶段才建立关联的新记录，不把重叠时期累加为额外工作年限。

## 本轮完成与交接

本轮纳入的任职关系与阶段明确；主要职责线有真实行动／事件或链接到已深入的项目；个人权限与团队分工可辨；交付与状态有来源；未展开项和关键冲突已分别处理；正文已保存并给用户看过。缺乏收入或效率数字不阻塞，只有职位和抽象职责则仍需深入。

单个项目讲清楚不能直接结束整段任职。完成本条后回到 progress 核对本轮其他范围；先做资产核对，按用户目标再交接母版。新进展仅重开受影响项，母版标待更新；保留历史阶段记录。

独立使用时按相同方法交付详细任职档案、项目关系和下一问；无 career 工具时不声称入库、同步或校验已完成。
