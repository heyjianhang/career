# 目标公司发现

回答“以我做过的工作和想去的地方，还有哪些公司值得了解”。先发现并核实公司，再找相关岗位；知名度、政策称号和个人适合程度分别判断。

## 接手与范围

在 Career 工作区先读 AGENTS、context/INDEX.md、context/state.md、context/goals.md 和已有目标公司索引；只读取与任务有关的简历／经历，复用已回答的偏好。遵循 AGENTS 选择桌面或 npm CLI，`resume list/read --json` 用于确定实际简历，`board overview --json` 用于查已有机会。不假定用户是开发者或已经有完整简历。

把“行业”与“做什么”分开：原行业、具体任务与能力、经验层次、意向城市／是否迁移、工作条件。用户没有材料也可先按口述方向做有限研究。只补问会改变筛选范围的缺口；已有明确城市就不再问。跨行业机会需说明能力迁移的依据与新增门槛，不能只因为都写了“AI”“运营”就推荐。

用户只要名单时做到有来源的初筛；明确要深入研究、找岗位或筛选入库时接着执行已授权范围。先给一批可评估结果，按新线索继续扩展；不强行凑满数量，不将有限样本称为全市／全行业排名。

## 发现与核实

按 [检索与判断](references/research.md) 从官方产业名单、行业与产品线索、企业官网和实际招聘交叉查证。公司分为“直接相关、能力可迁移、依据不足”并解释理由；优先级是本轮研究建议，不是用户收藏决定或岗位匹配分。

- 官网域名、法人、品牌、集团与子公司需要区分；多个城市的同一主体复用记录，不同用工主体不因品牌相同合并。
- 注册地、总部、业务团队所在地和岗位工作地点分别记录；没有当地团队／岗位证据时写待核实。
- 政策名单记录发布机构、批次、日期、认定层级和公示／正式认定状态。“获扶持”“小而美”都要具体证据，不从称号推断待遇、稳定性或管理水平。
- 招聘状态分为“找到相关岗位、仅找到招聘入口、暂未找到相关岗位、确认已关闭”。保留检索时间与链接；没有找到不等于不招人，长期人才库不等于当前空缺。
- 使用当前 Agent 的可用联网工具；企查查是可选的主体核实来源，按 career-company 的工具规范调用。没有联网能力就分析已提供材料、保留待核实线索，不能假装实时查过或把测试材料当企业事实。

## 保存与接续

按 [公司池与岗位交接](references/storage.md) 保存到 `research/companies/`：跨轮次复用稳定公司记录，搜索报告记范围、来源和筛选取舍。先读再合并，保留用户备注、手改和不再关注的决定。文件不存在时按需创建，不预置空公司或虚构 JD。

在“我的资料 → 目标公司”可阅读报告、公司记录和来源；求职看板的“发现公司”入口进入同一资料分类。页面复制指令交给工作区 Agent，不在后台自动运行搜索。保存后回读文件、核对链接，按既有保存／同步选择处理，并在 context/INDEX.md 和 state 留研究位置与下一步，保留原访谈断点。

后续按用户的实际目的衔接：

| 用户要做什么 | 使用的能力与交付 |
| --- | --- |
| 深入了解一家候选公司 | [career-company](../career-company/SKILL.md)，无 JD 时在公司池原记录补充分析；有具体岗位则写岗位 analysis/company.md，并引用公司来源 |
| 看这个方向通常要求什么、该补什么 | [jd-research](../jd-research/SKILL.md)，仅使用真正取得的 JD，保存到 research/jd/，引用公司 ID |
| 把选中的招聘机会放进看板 | [career-board](../career-board/SKILL.md)，按来源去重、原文入库，再回写公司记录里的岗位 ID 与链接；只有公司名不造岗位卡片 |
| 判断某份简历是否适合岗位 | [career-match](../career-match/SKILL.md)，核对 JD 和具体简历；未确定版本先推荐并让用户选择，不擅自绑定 |
| 准备简历、打招呼或面试 | 经岗位流程进入 resume-tailor、career-outreach 或 career-board 的面试方法；不把研究结论变成个人经历 |

先交付值得关注的公司及理由、招聘核实结果和限制，再说明已保存的位置。发现公司不自动投递、发送消息、改变岗位阶段或用户星级。不因本次研究建立后台定时任务；用户明确要求持续监测时才另行确认频率和可用执行能力。
