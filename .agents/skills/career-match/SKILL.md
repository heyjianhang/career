# 简历与岗位匹配

本 Skill 的判断对象是“这一份简历 × 这一份 JD”。不能把用户所有经历当成这份简历已经写出的内容，也不能只按职位名或关键词数量判断适合程度。

## 输入与版本

1. 先按工作区 AGENTS 确定 CLI。有关联岗位时读 `opportunity context --id <ID> --json`、`opportunity read --id <ID> --path job.md --json`、现有分析及摘要；用 `resume read --id <简历ID> --json` 取得实际内容和 SHA-256，按返回路径读取必要正文。旧版附件也要真正读取，不能只看标题或文件存在。必要文件不可读时明确限制。
2. 默认分析岗位当前绑定的简历。用户直接指定另一版本时，可以做标明版本的比较，不能把它写成当前绑定版的分析或静默换绑。没有绑定也没有指定时，让 [career-board](../career-board/SKILL.md) 推荐并确认版本；用户仅要比较候选简历时，逐份列明 ID，不自动决定绑定。
3. 报告保留岗位 ID、JD 来源／路径与摘要、简历 ID／名称／路径与摘要、分析时间。独立提供的文档没有 ID 时记录文件及可取得的版本依据，不杜撰 SHA。写回前重读绑定和输入摘要；已变化则重评，不能把旧结果标为最新。

## 分析与建议

阅读 [匹配方法](references/method.md)，先识别真实任务、明确硬条件及优先项，再做要求与证据对照。输出可以自由组织，但要能看出：匹配在哪里、缺口是什么、依据在哪、哪一处值得优先修改或询问。没有证据不是能力为零。

通常用文字给出“值得尝试／补清关键证据后再判断／存在明确冲突”及理由。用户要评分，或通过岗位匹配页的「开始分析／更新分析」交接时，按共享行为锚点评价并依 [总体评分保存格式](references/storage.md) 留存；网页计算汇总并展示口径、权重、覆盖和未知。不宣称 ATS 分数、录用概率或行业客观标准。不因关键词相似就推荐算法研究，也不因标题不同排除实际任务相符的应用交付岗位。

## 保存与交接

- 当前绑定版本的分析写 `analysis/match.md`。候选对比或用户指定的未绑定版本写单独文件（例如 `analysis/match-candidates.md`），注明尚未绑定；不能覆盖当前绑定版的结论。
- 修改前读原文件，保留有价值的用户补充和旧结论变化依据。用 `opportunity write --id <ID> --path <分析路径> --input <临时.md> --if-match <已有文档摘要> --json`；新文件省略摘要。命令成功才报告保存。
- 只建议如何调整表达。用户授权定制时交给 [resume-tailor](../resume-tailor/SKILL.md)，修改后的简历需重新核对匹配。明确能力缺口交给经历澄清或练习，不让措辞创造事实。
- 不修改绑定、用户星级、岗位阶段，不自动投递。仅有匹配分析不足以写综合五星推荐；上层按共享规则合并公司、偏好与匹配证据后决定是否有足够依据。
- 被委派为只读分析者时返回草稿、输入版本和关键未知，由上层校验并保存，不并发改卡片或自行联系用户。
- 用户接着要打招呼或整套投递材料时，交给 [career-outreach](../career-outreach/SKILL.md) 从当前版本的匹配证据选材；仅完成匹配分析不自动扩展。
