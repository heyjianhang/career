# 岗位匹配：最终交付什么

读者需要决定是否投递、简历怎么改、面试准备什么。分析针对指定版本，既不是公司背景调查，也不是对用户所有能力的评价。默认按下面顺序组织；可合并或改名，用户明确限定范围时遵循其范围。材料不足时写出缺口及其影响，不填充套话。

## 正文应回答的问题

| 内容 | 交付要求 |
| --- | --- |
| 总体结论 | 开头直接说值得投、补清什么后再判断、或存在什么明确冲突；用最关键的匹配证据和限制解释。不能只说“存在一定匹配度”。 |
| 主要匹配点 | 选择影响招聘决定的真实任务，说明本版哪个项目、本人做了什么、怎样对应岗位要求。框架清单不能代替交付证据。 |
| 差距与未知 | 区分硬条件冲突、已确认能力差距、简历表达遗漏、尚待确认。每个问题说明对该岗位的影响；“本版没写”不能变成“你不会”。 |
| 简历怎么改 | 按优先级指出具体章节／项目、保留或前移什么、补充哪项已知事实；证据充分时给一条可直接替换的示例。事实未确认时先提问题，不生成假经历。仅建议，不自动改简历。 |
| 面试或补足重点 | 围绕差距给可执行准备：讲清哪段经历、补哪个可核对的细节、练什么任务以及怎样验收。不要泛泛写“加强学习、提升能力”。 |

对照表是可选的分析载体，不是全部交付。使用时建议四列：**岗位要求｜本版简历证据｜判断｜行动**。每格写短结论，长的项目讲解、改写示例放表外。证据少时可以用短条目；不要用大表堆砌整段推理。

## 证据与措辞

- JD 写“使用 AI 编程工具”时，“做过业务 Agent”不直接证明前者；但也不能据此断言用户没用过。先查授权范围内已有事实，没有记录才标为待补充，并提出对应案例问题。
- 技术关键词、学校／公司名、职位名称不是自动加减分依据。JD 没写的条件不能升为门槛；明确差距也不能用其他优势冲抵。
- 用户其他事实可帮助发现遗漏，必须写成“已有资料补充，本版尚未呈现”，与简历已有证据分开。不要为了让结果好看猜测指标、扩大职责或把计划写成已交付。
- 正文引用“JD：岗位职责中的业务集成”“简历：知识助手项目／检索接口”，可用简短原文或可读链接。**不要在正文堆岗位 ID、文件路径、SHA、时区、行号和命令**；这些追溯字段放 YAML 文件头。用户主动要求技术审计时可另附明细。
- 公司经营、薪资谈判和用户离职经历属于公司／机会判断；这里只保留直接影响岗位条件的事实，不复制私人处境。

## 一个简短的合成示例

> **建议投递，先补清质量验证的证据。** 本版“知识助手”项目能支持检索与工单接口集成，和岗位主要交付相符；JD 要求的上线质量评估尚未在本版体现。现有材料不足以判断这项能力，不按没有经验处理。
>
> **优先修改：** 将知识助手项目放到项目经历首位，突出本人负责的检索链路和接口接入。评估部分先确认是否做过测试集、失败案例复盘及上线验收；有记录后再补进简历。
>
> **面试准备：** 用一次真实查询说明检索、调用接口、异常处理与结果返回，并准备一个失败案例及修正过程。

示例只说明写法，不是可复用的用户事实，也不代表所有岗位都需要质量评估。

## 完成检查

正文能让用户回答“是否值得投、证据是什么、下一步具体做什么”才算交付。生成页面总体结果还须遵循 [保存协议](storage.md)，通过输入版本及评分校验；全未知可以无数值，不能编造分数。格式校验不证明结论正确，仍须逐条回看 JD 和实际简历。
