# 总体匹配与详细分析的保存

岗位「岗位匹配」页上方展示总体结论、匹配分、证据覆盖与必要条件，下方渲染同一份 `analysis/match.md` 的正文。其元数据使用 [career-match/v1](../../../../schemas/match.v1.schema.json)，从输入版本与逐项评分计算汇总，不把卡片的个人星标当匹配度。

当前绑定简历的主报告默认包含总体结果（用户明确只要文字时例外）；在页面发起或用户明确要求评分时必须提供。按 [匹配方法](method.md) 先定任务、锚点与权重，再写以下元数据。普通文字分析仍可不评分；旧文档原样可读，界面显示尚无总体评分，不推测其分数。

```yaml
schema: career-match/v1
opportunity_id: <当前岗位ID>
resume_id: <本次所用简历ID>
resume_sha256: <resume read 实际返回的摘要>
jd_sha256: <opportunity read job.md 实际返回的摘要>
assessed_at: <带时区的 ISO 时间字符串>
summary: <简短总体结论，说明主要匹配与限制>
criteria:
  - id: <从该岗位任务提取的维度名>
    weight: 100
    score: null
    evidence: []
    reason: <为何符合、部分符合或尚无法判断>
hard_conditions:
  - label: <JD 中明确的必要条件>
    status: unknown
    reason: <原文位置与本版证据，说明已知或待确认>
```

这只是字段示意，不能将占位符写入实际文件。将实际 YAML 放在文件头 `---` 之间，其后按 [最终报告要求](report.md) 写面向用户的结论、证据、差距及具体行动；不要在正文重复这批技术元数据。原文、证据与用户补充保留，未知字段不随意删除。

- `criteria` 是所选简历的能力匹配表，维度名称唯一；实际权重合计 100。每项 `score` 为 0–4 整数，未知使用 `null`，不能补成 0 或 2。已评分项必须有 `evidence`（简历具体章节／条目及对应 JD 要求，用可读名称定位），所有项都有 `reason`。不要把工具词拆成多条来重复加权。
- `hard_conditions` 单列必要条件，状态为 `met`（符合）、`unmet`（明确不满足）、`unknown`（待确认）；没有明确必要条件可以为空数组，正文说明核对范围。不能把优先项升为硬门槛，不能用高平均分掩盖明确冲突。
- 网页按共享公式计算已知项得分 S、证据覆盖 C、未知极值 L–H。星形只是 S 在百分制中的可视化；并非综合推荐五星、用户个人星标或录用概率。没有已知项时不评分，覆盖不足时突出补充信息的需要。
- 所用简历与 JD 的摘要、岗位绑定变化后，网页保留并标明历史分析。必须重新读取并判断后才更新摘要，不能只改元数据让旧分析变新。
- 用户指定另一份未绑定简历时另存候选比较稿，不能覆盖当前绑定版本的主分析。缺简历时先推荐并确认，不虚构通用分数。

保存前读旧稿；用 `opportunity write --id <岗位ID> --path analysis/match.md --input <候选文件> --if-match <旧文件摘要> --json` 写回，新文件省略 `--if-match`。重读绑定与输入摘要、保留用户补充，冲突先合并。需要总体结果时，先运行 `opportunity match-check --id <岗位ID> --input <候选文件> --json`；通过后保存，再运行 `opportunity match-check --id <岗位ID> --json` 核对落盘结果。CLI 与页面复用评分校验，检查元数据、权重、证据字段、当前绑定和输入摘要，且要求有正文；缺少格式、输入已变或没有正文会返回失败，不能当已完成。全未知且理由明确可通过，但不显示数值。

`board check` 只检查通用文件结构，不证明匹配报告完成。`match-check` 也不验证语义真实性、来源是否支持结论或改写质量，必须按报告要求人工复核。普通旧文字报告仍可阅读和保存，不从正文猜分；用户要求补成页面结果时须重新读取材料评估，不能给旧稿硬套分数。
