# 母版的增量更新

## 定位变化

先读已有条目、维护清单和本轮事实。若新信息尚未进入 facts，先由 intake 保存来源和事实，再更新表述。纯措辞调整不修改事实内容。

| 变化 | 处理范围 |
| --- | --- |
| 新增项目／任职 | 建立对应母版条目，加入索引；必要时补充相关任职要点和简介 |
| 原项目上线、增加成果或改变状态 | 沿用原项目及母版 ID，只更新涉及的职责、过程与成果 |
| 纠正日期、个人职责或数字口径 | 查找所有引用该事实的母版条目，并检查组合正文中的重复表述 |
| 新教育、技能、语言或证书 | 更新事实与索引直接引用，复核展示；不凭空创建同类型 master-entry |
| 基本信息变更 | 更新 profile 与受影响的简介，重新组合展示 |
| 用户调整表达 | 先保留原精修文字，再修改用户指定部分；如引入新事实，转 intake 核对保存 |

母版已在多处引用同一事实时，查找 source_ids、based_on 和索引引用来确定影响范围；不要只改最先找到的那一个条目。

## 更新顺序

1. 清单记录事实变化与待更新对象。初期完成日期保持为历史里程碑，母版当前状态改为待更新。
2. 对照事实修改相关正文，保留未受影响内容、稳定 ID、用户润色和未知字段。组合条目的全部来源继续保留。
3. 复核简介、任职与项目是否仍一致；新事实不一定要写进每一层，只在改变表述时调整。
4. 实质核对后重新计算涉及事实的 based_on，检查引用和索引。只为清除告警而更新摘要会掩盖内容未同步，不能这样处理。
5. 读取已有可读预览，保留用户直接编辑的内容。将有依据的修改纳入事实／母版来源，再生成更新的完整预览；无法判断时保留原文件并另存候选，记录待处理差异。
6. 校验、展示本轮变更，将已处理项目的同步状态恢复为本轮已整理。其他待更新项继续保留，context/state 指向下一项。

当前母版可持续编辑；历史已冻结的版本维持原样。本轮维护只更新当前母版及派生预览，不批量改历史版本。

## 一个持续维护例子

用户说：“上次那个报名系统已经上线，有三场活动用了。”先更新原项目来源与事实，核对“三场活动”是实际使用范围；再把母版的试用表述更新为有依据的上线与使用情况。沿用项目 ID，不新增重复经历，也不把三场活动扩写成用户增长或收入效果。
