# 项目深挖的具体方法

这些维度用于 Agent 判断下一问，不是发给用户的问卷。先读已知材料，只问当前理解缺口。一轮通常一个主问题，可以带一个帮助回忆的小提示。

## 从名词转向真实场景

| 已有回答 | 接着理解什么 | 可选择的一问 |
| --- | --- | --- |
| “做了一个平台” | 服务对象、原流程和问题 | 当时谁在什么情景下需要它，原来怎么处理？ |
| “我负责这个项目” | 本人责任与决策权 | 哪些由你定，哪些要别人批准，哪些是同事实现的？ |
| “推动了落地” | 关键动作与协作 | 选一次推进最不顺的节点，你当时具体做了什么？ |
| “做过很多优化” | 实际问题与选择 | 选其中一个，你怎么发现问题，为什么这样改？ |
| “效果很好” | 实际交付与依据 | 谁已经在使用，哪些变化是你实际观察到的？ |

这只是可选问法。已经讲清楚的内容不要换词重问；“没有困难”“没有数字”都可以是真实答案。

## 按项目的真实工作线展开

先列出用户材料里出现的工作线，例如需求、实施、验收、运营，不默认每个项目都有这些阶段。选择当前一条深入，记录它的起止与相互依赖；未讲部分在 maintenance 标明。复杂项目应解释前后阶段为何变化，不只列一串成果。

项目整体周期与本人参与周期分开，个人角色可能中途变化。记录谁提出目标、谁作决定、谁实际执行、谁验收；“组织评审”和“拥有最终决策权”不等同。团队人数与实际管理人数分别核对。

## 按角色选择细节

- 项目／产品负责人：目标与范围如何确定、验收依据、资源与依赖、优先级冲突、变更处理、推动方式、决策权限。选实际事件理解，不因职位名预设其管理预算或人员。
- 技术／AI 应用：业务与系统边界、本人设计或实现的部分、数据与权限、选型依据、调试与验证、实际部署阶段、失败处理。用户讲到何种技术就深入何种技术，不强加 RAG、训练或大规模系统。
- 运营／业务：用户或客户、渠道与流程、本人动作、合作关系、资源限制、反馈与转化口径。区分人次与人数、活动结果与业务收入，不把相关性当成贡献因果。
- 设计／研究／学习实践：研究问题、方法、作品与实验、迭代依据、本人和团队贡献、适用边界。课程演示和生产应用分别记录。

## 一件事怎样追到可复用

用户说“需求不断变”时，先问一次实际变化，而不是马上给项目管理建议。收到案例后，围绕其中缺口继续：谁提出、原约定是什么、本人怎样理解影响、实际讨论过哪些方案、谁决策、如何执行、如何验证、后续是否又调整。把回答逐次保存进同一事件段落，别等故事“精彩”才写。

用户说“我只是帮忙”时不急着拔高：先问实际承担的一件小事、输入输出和协作对象。准确的执行细节本身有价值。对“独立完成”也核对上下游，不能自动当成全部由本人完成。

用户给出整份方案时，区分方案写了什么和真正做了什么。源码与附件能补实现细节，不能独立证明作者贡献、采用范围或业务结果。

## 结束与后续

保存时用一个“主张—依据—边界”的反查：例如“带团队”有哪些实际管理行为，是否只是项目协同；“系统设计”哪些选择由本人提出；“降低成本”有何基线与统计口径。把“做了什么”“为什么这样做”“如何知道有效”分开核对，缺哪一层就问那一层，不因内容长而停止。

遇到方案与结果混写，保留当时所知和后来发生的事情；用户的复盘是经验资产，但不能倒写成当时就作出的正确判断。对未采用方案也记录原因、约束和学到什么，价值不只来自成功结果。

用 [项目 Skill 的标准](../SKILL.md#何时算这一项本轮整理完) 回读。事实尚浅时留下明确下一问，例如“试点验收里，你负责设计哪些检查项，谁决定通过？”，而不是“继续补充细节”。已清楚的部分不反复盘问。用户暂不回忆时保存断点；以后新增进展更新同一文件并保留时间语境，不把后来结果写成当时已知。

可选公开网页、演示与作品在理解项目后顺带问一次。内部核对附件不默认转成公开链接。量化结果没有统计就保留实际完成范围。
