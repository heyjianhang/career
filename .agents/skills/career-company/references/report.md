# 公司分析：最终交付什么

交付帮助求职者判断这份机会的报告，不是工商信息汇总、聊天记录或个人处境复述。默认先结论再依据，下面是必须考虑的内容，不强制固定标题或八章模板。用户只问一个具体问题时可缩小范围；资料不足须明确“初步判断”及缺失影响。

| 内容 | 要写什么 |
| --- | --- |
| 当前结论 | 建议继续了解、先核实某个关键条件、或不建议优先投入，以及改变判断的关键条件。不要把未知写成确定风险。 |
| 公司在做什么 | 已核实主体、主要产品／业务、客户与收入模式；区分官网宣传、已知交付与未知。无需罗列无关工商字段。 |
| 岗位与团队 | 这份岗位实际要交付什么、招聘动机、团队分工与可用资源；JD 可支持什么，哪些需向招聘方确认。无证据不推断团队人数或业务成熟度。 |
| 值得关注与风险 | 说明已知事实对用户目标的具体影响，分清吸引点、明确冲突和待核实事项。注册资本、融资新闻、匿名评价不单独证明现金状况或工作体验。 |
| 下一步 | 给出优先核实的问题及用途，例如“确认前三个月交付、谁提供数据、由谁验收”，并说明哪些回答会改变是否继续的建议。 |
| 主要来源 | 关键结论旁用可读链接，末尾简列来源标题、日期、支持什么及研究限制；用户转述标注来源身份，不写成公开已核实事实。 |

## 内容边界

用户偏好可以用于判断，但只写与决定直接相关的条件，例如“招聘范围低于你的目标，先确认预算”。不展开用户原公司的矛盾、聊天原话、私人关系和心态，更不能把旧工作的问题投射成新公司的事实。简历逐项比对、技术能力评分与简历改写属于 [career-match](../../career-match/SKILL.md)。

正文不放 UUID、SHA、内部文件路径、检索日志、命令或时区等技术记录。核实日期可放简短署记，正文以业务、岗位与行动为主。追溯信息保留在不渲染的 YAML 文件头；本地资料用“招聘原文”“面试沟通记录”等名称定位，公开来源用链接。不要删掉可核实的来源，也不要用假链接装饰结论。

## 一个简短的合成示例

> **可以继续了解，先确认岗位交付与工程支持。** JD 明确要求把知识助手接入业务系统，与希望做应用落地的目标一致。但目前只有招聘方材料，尚不能确认团队分工和上线支持。
>
> 公司业务介绍将知识管理作为产品方向；这只能证明其公开定位，不能证明已有客户规模。面试优先问最近一次上线交付、本人负责范围、数据与测试支持，以及试用期验收方式。得到具体案例后再判断是否值得进入后续流程。

以上是写法示例，不是任何真实公司的结论。实际报告必须附当次查到的来源；查不到就明确限制，不为凑完整栏目编资料。

## 保存前复核

检查每个判断是否有事实支撑、公司主体是否一致、待确认是否被写成结论、用户能否据此安排下一步。更新保留仍有效的证据与用户笔记；变化原因简短说明，不将过时结论继续当当前事实。正文结构符合要求不等于已完成独立尽调。
