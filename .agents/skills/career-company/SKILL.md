# 公司分析

回答“这个公司的这份机会，值得这位用户继续了解吗”。仅查询工商信息不算完成研究；不要求先有简历，也不要求用户先配置付费服务。

## 接手与研究

1. 遵循工作区 AGENTS 的 CLI 入口。读取 `opportunity context --id <岗位ID> --json`、`job.md`、已有 `analysis/company.md` 与用户已表达的偏好。只分析公司时，可直接接收公司全称、官网和用户问题，不强制建卡。
2. 先读 [研究方法](references/research.md)。确认招聘品牌、法人、用工主体、部门和地点的边界；同名候选无法确定时提出一个具体问题，不将多个公司的资料合并。可以继续研究已确认的品牌业务，但不得把未确认主体的工商数据当它的事实。
3. 查看本机 `company status --json`。可用且需要工商证据时按 [查询与保存](references/tools.md) 调用企查查；未配置则简短说明“企查查未配置，可在设置 → 外部服务中添加；本次先用公开资料研究”，继续使用当前 Agent 已有的联网搜索。没有联网工具则只基于已提供材料做有限分析，说明未核实的部分，不假装查过。
4. 围绕当前决定检索，优先官网、产品与正式披露，再用招聘原文、可靠媒体和可访问的员工评价交叉核对。工具失败不等于公司有问题；不要绕过登录或访问验证。企查查权限、额度等错误停止重复调用，说明影响并改用可用来源。
5. 将证据解释为岗位影响：这家公司做什么、这个岗位承担什么、完成工作需要谁和哪些资源、与用户目标哪里一致或冲突。按初筛／面试前／Offer 的实际问题决定深度，不机械填满八个维度。

## 公司池中的独立研究

由 [目标公司发现](../career-discovery/SKILL.md) 接入且尚无 JD 时，先读其指定的 research/companies/companies/<公司ID>.md、用户偏好与原证据，按 [保存协议](../career-discovery/references/storage.md) 把深入研究合并回同一公司记录。保留用户关注状态与笔记，标明新增证据、日期和变化原因；不要为保存公司分析先建一个虚构岗位。未指定文件时先查公司池索引去重。已有具体岗位时继续使用下述 analysis/company.md，记录适用于该团队和岗位的判断，不把公司总体材料直接当个人匹配结果。

## 交付

写作前读 [最终报告要求](references/report.md)。先给是否继续了解的结论，再说明公司业务、岗位与团队、机会与风险、核实问题及下一步。标题和篇幅按材料调整，但不能用聊天回顾或资料清单替代最终分析。公司宣传、员工个案和你的推断分别表述。查不到财务不等于经营差，工商正常不等于管理好；不要根据集团名气推断某个团队。

岗位内保存到 `analysis/company.md`，保留用户笔记和仍有效的旧证据，说明改变结论的原因。先读现有文件和摘要，再 `opportunity write --id <ID> --path analysis/company.md --input <临时.md> --if-match <摘要> --json`；新文件省略摘要。返回实际路径和研究限制。无法取得关键证据时交付初步分析，不能宣称完整尽调。

不改简历绑定、用户星级、岗位阶段或实际投递状态。只做公司分析时不另外生成简历匹配分。需要比较机会价值时使用 [共享评价方法](../career-board/references/job-evaluation.md)，先核对用户偏好，不能把企业通用分冒充个性化推荐。

由上层 Agent 委派且约定只读时，返回带来源的报告草稿、所读文档摘要和未解决项，由上层保存；不自行询问用户或同时修改卡片。
