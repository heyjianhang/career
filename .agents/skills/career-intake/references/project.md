# 项目经历的维护

## 开始与判断

用户说“我最近做了一个项目”时直接进入这里。先引导：“我们来维护这个项目，先说它解决什么问题，以及你主要负责什么。”结合名称、单位、时间和已有 ID 判断新项目还是原项目的新进展。

## 访谈与专业判断

- 项目可以是业务活动、研究、运营改善、设计作品或技术系统。先问服务对象、问题和目标，按实际类型追问，不默认要求技术栈。
- 分清项目整体范围、本人角色、具体行动和团队成果。围绕关键选择及困难了解贡献，而非仅罗列工具名。
- 区分本人参与时间与项目整体周期，项目属于哪段任职，有没有独立组织或委托方。
- 状态区分构想、完成部分、演示、试用、上线和持续维护；代码或截图只能证明观察到的实现，不能推断上线、真实用户、收入或个人独立完成。
- 效果可为具体交付、使用反馈或有口径的数字。尚无效果数据时保存实际完成范围和待观察事项。

## 保存

用 [project 模板](../templates/facts/project.md)，保存为 `resume/facts/projects/<id>.md`，稳定 ID 使用 `project-*`。项目描述、本人职责、过程、成果和材料分开写；有任职关联时填写 employment_id，无关联才记录实际 organization。链接与附件保留来源定位，按 [落盘步骤](saving.md) 更新问题与状态。

## 本轮已整理与后续更新

服务对象／问题、本人角色、关键行动、当前交付／状态已清楚并展示，未知指标保留缺口，即可标记本轮已整理。项目仍在进行也可以完成本轮资料整理，is_current 按真实状态保存，不把两种“完成”混用。

“后来上线了”更新原 ID、来源、状态与成果；“又做了另一个项目”才建新 ID。阶段结果可在同一事实正文按日期补充，保留旧阶段语境。保存后将关联母版项目、任职和必要的简介标为待更新。

## 项目链接（可选）

项目表达已清楚时，可顺带询问是否有可展示的项目网站、演示、源码或作品介绍；没有就继续，不作为完成条件。按 `{label, url}` 保存到该项目事实的 links，并在补充材料说明展示选择。不要把内部系统入口、登录凭据或仅供核对的材料当作公开作品链接。母版保留链接与所属项目关系，生成时交给对应 item.links；多个链接可分别命名“项目演示”“源代码”“作品介绍”。
