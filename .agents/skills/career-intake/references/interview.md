# 按缺口推进的访谈

先提取用户已经说过的信息，不重复索取。目标是让下一轮补充改变记录质量；没有必要的问题不问。以下问题是分支题库，不是一次性问卷。

## 选题顺序

先解决“这是谁做的、何时做的、做到了哪一步”的歧义，再讨论效果数字。已经能准确表达的内容先保存。

| 当前表述／缺口 | 适合的追问 | 需要避免 |
| --- | --- | --- |
| “这个系统大部分我做的” | 哪些模块或决策由你负责？谁负责需求、测试、部署或协作？ | 自动改成独立全栈、项目负责人 |
| “有人在用” | 谁在用、在哪个流程使用？注册账号、活跃使用人数还是累计用户？ | 将用户数当并发、付费客户数 |
| “效率提升很多” | 原来怎样做，现在怎样做？有可比较的时间记录吗？ | 要求凭感觉给百分比 |
| “做了一个 Agent” | 你解决的业务步骤是什么？你设计、集成、验证了哪些部分？ | 根据依赖名推定精通某框架 |
| “毕业项目／侧项目” | 演示、内部试用还是已上线？本人完成范围是什么？ | 按生产项目描述未部署作品 |
| “活动／销售／运营工作” | 对象与目标是什么，你采取了哪些具体行动？结果由谁记录？ | 套所有人必填的技术题 |

## 挖掘被遗漏的贡献

围绕一个具体事件推进：当时的障碍 → 你作出的选择 → 实际执行 → 产生的变化 → 可找到的依据。可追问协调、异常处理、交接培训、维护和复盘等旧简历容易省略的工作，但不能先假定这些都发生过。

用户只提供代码时，可先整理模块和实现观察，再核对本人职责、上线状态与业务效果。提交次数、代码行数和仓库所有者都不能单独证明贡献比例。

## 零散材料与中断

材料多时先列已有材料的短索引，选当前最相关或用户最愿意讲的一段。不要必须读完全部代码才开始访谈。用户中断时保存已经明确的事实和待补充项，state 指向具体记录，下一轮不从基本信息重新问起。

## 虚构小例子

输入：“我参加了书店的四次读书活动，主要管报名。”

先保存参与四次活动和负责报名整理的自述；追问“你还负责到场确认或反馈吗？四次活动的参与人数有记录吗？”只有得到回答后才增加相关职责或人数。即使没有统计，也可保留准确的定性表述，不补造增长或转化率。
