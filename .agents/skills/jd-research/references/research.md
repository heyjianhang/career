# 从岗位样本到需求判断

## 采样由问题决定

先写明研究范围：目标岗位／待比较方向、地区、资历层级、来源渠道、用户排除条件和采集日期。用户没有要求排除外包、实习或某类企业时，不把这些个人偏好写成通用过滤规则。

按“职位别名 × 核心任务 × 行业或企业类型”分批搜索。例如运营岗可从活动、用户增长、客户运营展开；AI 岗可区分应用开发、知识检索、平台工程和算法研究。避免把全部查询都限定在某个工具名，再将该工具的高频出现解释为全市场需求。

先小批取得正文、校准分类，再扩大覆盖。每批记录查询词、过滤条件、来源、时间、取得与失败数量、是否带来新的任务／要求。用户要求多采集时继续补足来源与方向覆盖；新增要求趋于重复时可结束并解释停止依据，不为凑数量堆重复卡片。平台出现登录、验证或限流则按该工具边界停止对应采集，继续使用可访问的公开来源或已取得材料；不把访问失败当成“没有岗位”。

## 样本台账

至少保留：稳定研究 ID、公司／职位、城市、薪资原文及周期、学历／经验原文、来源链接或材料名称、取得时间、正文完整度、岗位族、用工判断及依据、纳入决定及原因。发布日期、页面可读日期与采集日期不同；缓存、过期、关闭和未知状态明确标注。

完整正文、部分正文、纯列表／搜索摘要分开。链接打不开时只算线索，不能根据常识补全 JD。截图先辨认文字；模糊条件留待确认。原文与结构化标注分别保留，分析表只引用必要短句；对外分享不默认附整篇第三方 JD。

### 去重与过滤

- 平台岗位 ID 与规范链接用于发现同一职位；保留原始来源。只去掉已知追踪参数，保留有语义的职位 ID、查询条件和路由片段。
- 同岗多平台、同公司多城市的重复招聘模板可归为一个需求样本，同时保留不同机会。职责或职级不同就分别计数。不能仅按标题、相似关键词或同公司去重。
- 雇主主体、招聘品牌、实际团队、签约主体不一定相同。明确“外包／派遣至客户”有原文才按其认定；公司名像供应商、岗位涉及客户交付，均不足以证明该岗位外包。猎头匿名客户、驻场和主体不明单独列为待核实。
- 研究样本与投递清单分开。用户学历不符合的岗位仍可用来理解另一层级的需求，但不能混为“适合直接投”。不要因为用户暂时不会某能力就删掉该样本，造成需求偏差。
- 列表和正文的学历／年限／薪资冲突并列保留，记录向招聘方核实的问题，不静默选择较宽松的一项。

## 提取与归类

每条重要要求保留原句和段落定位，并标注为：明确要求、优先项、工作职责、工作条件、明确不要求或语义不清。不要把“有 X 更佳”算成必备，不把“无需 X”当需求；公司介绍、相邻职位和福利广告不参与能力统计。

先按真正的工作任务形成岗位族，再给能力维度起名，保持适当粒度：例如“设计评估与改善质量”与“具体评测工具”分层，避免某一技术独占整个能力。一般综合任务能力、专业知识、工具与方法、交付协作、学历／资格门槛和工作条件；按领域调整，不套固定 Agent 技术表。

同一岗位多次提及一个能力只计一次；父类不能简单把子类频次相加。明确要求／优先项／职责分别统计，它们可以在同一岗位共存，分列数之和未必等于总数。正文未提到只能表述为“未明确提及”，不能断言工作中用不到。

## 呈现结论

先按岗位族说明典型任务和差异，再讲总体共性；标出每组样本量、来源分布及同一企业集中度。小组样本很少时列例子，不给稳定趋势判断。薪资保持城市、级别、币种、薪数与职责口径，不能将混杂样本平均成用户应得薪酬。

推荐用这条证据链写结论：

> 多份 JD 的明确任务 → 企业可能要解决的问题（推断）→ 面试可能要求的证据 → 用户可用经历／待核对项。

例如招聘正文反复要求异常处理与交付验收，可以推断其关注实际交付可靠性；不能由此断言某家公司现有系统频繁失败。每个关键结论引用代表性岗位 ID／链接，频次来自完整样本表，不能用少数摘录冒充总体统计。
