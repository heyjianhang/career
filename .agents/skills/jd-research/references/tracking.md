# 研究资料、行动与简历的跟踪

在 Career 用户工作区使用 `research/jd/<日期-主题>/`。独立使用时采用用户指定目录。目录与记录 ID 一经使用保持稳定，新增样本继续追加；不要每次重新研究而丢失以前的判断。它们是普通研究文件，不是个人经历实体或新的评分 Schema。

## 一份研究保留什么

| 文件 | 内容 |
| --- | --- |
| `report.md` | 研究目标、日期、范围、批次统计、岗位族、需求结论、证据映射、限制、下一步，以及结论变更记录 |
| `samples.md` 或 `corpus.json` | 一份主样本台账；稳定样本 ID、公司职位、原始链接／材料位置、采集时间、正文完整度、去重组、纳入原因和失效状态 |
| `sources/` | 实际取得的正文／截图／附件，按样本 ID 关联；已有看板 `job.md` 可直接引用，不重复维护原文 |
| `plan.md` | 需要多轮跟进的补表达、待访谈、学习实践和待核实事项，逐项记录状态与依据 |
| `statistics.json` | 需要复算时保存脚本实际结果；由主台账派生，不手工维护第二份计数 |

少量样本可用 Markdown；批量统计时按 [统计契约](corpus.md) 用 corpus 作为主台账，不再维护平行的完整 samples 表。每次抓取都记录结果，包括部分正文、链接失败和排除项。页面后来变化时保存新快照与日期，旧引用仍能查到；比较不同批次，不把同岗的历史快照重复计为当前需求。

原文里的会话参数、Cookie、访问令牌不保存。私人附件按用户的保存／同步选择处理，不将完整第三方正文默认公开分享。

## 从要求到行动

在报告内维护以下映射，ID 可用 `req-001`，不要只有一句“建议加强某技能”：

`要求 ID／任务 → 岗位族与样本 ID、原文位置 → 要求性质 → 事实 ID／文件与具体片段 → 证据状态 → 建议行动 ID`

明确要求、优先项和职责分别记。证据状态区分已支持、待深挖、部分支持、未知、确认缺口；岗位要求不写入个人事实。未知项先核对，已支持但没出现在简历中的内容进入表达建议。

计划条目至少包含：稳定 ID、关联要求／样本、类型、具体下一步、完成依据、状态、最近更新及产物位置。时间未知时写建议安排，不伪造用户承诺。类型使用“补表达／待访谈／学习实践／条件核实”；状态可用“待开始／进行中／等待补充／已完成／暂缓”。只有实际执行并满足完成依据才标已完成，阅读课程不等于获得工作经验。

用户补充经历时先写 facts，再更新映射；纠正事实时保留原因和受影响表达。新样本推翻旧判断时记录旧结论、变化依据和新的适用范围。用户改方向可新建一份关联研究，保留原范围，不回写旧投递记录。

## 如何让下一位 Agent 找到

- `context/INDEX.md`：当前研究的路径、主题和报告日期。
- `context/progress.md`：本轮是否包含研究、覆盖范围、实际阶段及剩余项；不复制全部计划。
- `context/state.md`：当前样本／行动 ID、下一步或待问问题，并保留暂停的经历访谈断点。
- `resume/questions.md`：只收履历事实问题，链接研究要求；学习清单仍留在 plan。

Career 的“我的资料 → 岗位调研”可读这些文件；`history save` 与已连接的云同步会纳入 `research/jd/`，其他任意 research 目录不自动纳入。只做本机文件保存也可继续；没有 Git 或上传失败，分别说明文件已保存和同步未完成，不声称已有备份。

## 简历生成时怎么用

先检查研究的范围、更新时间和未完成事项，再读取当前事实、母版及内容包的手改。只用有依据的事实满足需求；研究结论帮助排序与选材，不成为个人事实来源。

在报告的“简历使用记录”追加：简历包 ID／路径、生成或修订日期、采用的方向与要求 ID、选用的事实／母版、仍未覆盖的要求及原因。不要把研究文件当作不兼容的实体 ID 塞进内容包 `source`。无需复制整份简历到报告，也不因出了一份简历把学习计划全部打勾。

下一次更新同一简历先读这条关联与最新包，检查新样本或新增经历是否影响现有选材；保留历史记录和用户手改。研究样本不自动全进看板，只有用户选定或已授权筛选入库的机会才建立卡片。
