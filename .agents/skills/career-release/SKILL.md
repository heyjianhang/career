# career 版本发布

只在 `heyjianhang/career` 开发仓库执行。先读根目录 [AGENTS](../../../AGENTS.md)、[项目状态](../../../docs/context.md)，检查实际分支、未提交改动和发布进度。此 Skill 留在源码仓库，不进入 npm 包或用户工作区；个人资料同步由 career-git 负责。

## 任务入口

- **准备版本、问发布还缺什么**：完成版本检查、说明和本地验证，列出尚缺的证据；不因此推送、发布 npm 或改 GitHub 设置。
- **发布指定版本**：读取 [发布操作](references/release.md)，按当前已完成阶段继续。沿用本轮明确的提交、推送和发布授权，不重复询问已授权步骤。
- **桌面安装包**：读取[桌面构建说明](../../../docs/desktop.md)，维护 desktop/package.json 的独立版本并验证真实安装包；Windows 与 macOS 分别构建，签名／公证与公开上传仍按本轮授权执行，不因打包就更新 npm 或门户版本。
- **维护门户版本／查看下载统计**：读取[门户管理 CLI](references/portal-cli.md)，使用 `npm run --silent portal -- … --json` 复用后台接口；先查登录状态，再保存草稿、验证和按授权发布。登录一次后复用本机短期会话，不记录管理密码。
- **分支保护是否开启／如何配置**：读取 [主分支保护](references/branch-protection.md)。先查询真实配置；检查和建议不等于授权修改设置。

## 每次发布的顺序

1. **确认范围**：比较上一发布标签与待发改动，区分已经发布、仅在源码实现、仅门户更新。报告改动与兼容性，确定新版本；保留不属于本次发布的未提交内容。
2. **在发布分支准备**：默认 `release/v<版本>`，从核对后的 `main` 建立。先更新 package 与锁文件，再核对下表；准备中文发布说明。不要为了发版清空工作树或覆盖用户文件。
3. **检查候选版本**：运行本地基础检查和相关专项检查，验证实际 tgz 安装；按明确范围提交，推送分支、创建 PR，核对该候选提交的三平台 CI。改过候选内容就重新检查受影响部分，并等新提交 CI。
4. **发布 npm**：从干净、已检查的候选提交生成最终归档，安装并验证这个归档。核对包名、版本、账号、清单和完整性后发布同一文件。只有 registry 返回新版本且新目录安装成功，才进入下一步。
5. **更新公共入口**：npm 验证后合并 PR，检查合并结果；把 `v<版本>` 标签指向实际发布归档对应的源码提交。更新发布记录、项目状态与 GitHub Release；门户重新构建并按已有托管流程部署。
6. **完成核对**：分别确认 npm 与安装指南、桌面 GitHub Release 与门户下载记录相符；两条发布线的版本不必相同。没有部署就明确“门户待部署”；不能把本机构建当成公网已更新。

`main/install.md` 是稳定的 npm 安装入口；新 npm 版本尚未能安装时，不提前合并修改该入口的发布 PR。门户主入口独立展示桌面安装包，以 site/downloads.json 提供静态快照；管理后台部署后可在验证公开安装包后切换运行时版本，不从本地候选版本自动生成可用下载。后台切换不代替 GitHub 发布、安装验收和静态回退快照维护。普通功能开发可照常通过 PR 合并；只改门户且不影响随包文件时无需抬 npm 版本。

## 版本从哪里来

| 位置 | 何时维护 |
| --- | --- |
| `package.json`、`package-lock.json` | 每次 npm 发版同步更新；版本事实来源，使用 `npm version <版本> --no-git-tag-version` |
| `install.md` | 更新推荐包版本及 setup 命令；保留仍适用的旧版本兼容说明 |
| `docs/installation.md` | 更新面向新用户的版本示例；换机仍遵守原工作区锁定版本，不一律升级 |
| `desktop/package.json` | 桌面候选版本，与 npm 独立；仅抬版本或生成本地产物不会开放下载 |
| `site/downloads.json`、`site/index.html` | GitHub Release 公开且实际下载校验后，填写桌面版本、tag 与各架构 URL；未发布项保留 null。构建生成徽标与按钮，不手改 build/site。详见[门户下载维护](../../../docs/portal.md#桌面下载入口) |
| README、`docs/get-started.html`、`llms.txt` | 短入口 URL 通常不变；入口变更时核对 `check:docs` 与 `scripts/bootstrap.mjs` |
| `docs/releases/<版本>.md` | 发布前写变化、兼容性与待验证项；成功后补日期、源码 SHA、归档完整性、CI 和安装证据 |
| `docs/context.md` | 发布成功后更新当前真实状态，明确仍未发布的本地改动 |
| Schema／平台模板 revision | 只有对应契约变化才改，不随 npm 版本机械递增 |

搜索上一版本的引用，逐项判断用途；不要全仓替换，旧发布记录、兼容性说明和历史证据应保留。测试应核对当前 package 版本而非硬编码旧值。

## Git 与交付约定

使用有意义的中文说明，例如 `fix(setup): 保留已有工作区的同步选择`、`chore(release): 准备 v<版本>`、`docs(release): 记录 v<版本> 发布验证`。只暂存明确属于本次发布的文件；提交前查看暂存差异。详细 PR、标签、发布说明与失败续接方法见 [发布操作](references/release.md)。

发布完成的回报包括版本、npm 与 GitHub 链接、发布源码提交、实际验证和剩余部署事项。只检查或准备时，直接说明没有发布。不要将登录成功、CI 通过或 main 已推送单独视为发版完成。
