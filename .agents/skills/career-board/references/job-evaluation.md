# 岗位评价、评分与推荐 v1

这是 career 自定义、可解释的决策辅助规则，未经过录用结果校准。不是面试概率、ATS 分数或客观人才等级。用户要评分／比较或需要透明排序时才计算；普通分析可以给条件式建议。用户五星不受此方法修改。

## 1. 识别实际岗位

从 JD 提取主要交付、关键任务、情景、要求的独立程度、硬条件与加分项，保留原文定位。以“需要完成什么”合并同类关键词，避免 Python、LangChain、RAG 分别重复计算同一能力。

| 实际产出 | 核心证据 | 不能冒充 |
| --- | --- | --- |
| 模型接入业务、检索、工具调用、评估和部署 | 应用链路、权限、失败处理、交付验收 | 调用 API ≠ 训练算法 |
| 数据集、训练实验、算法改进、研究指标 | 数据与实验设计、基线、对比、可复现结论 | 做过 RAG ≠ 做过训练 |
| 客户方案、演示、实施交付 | 需求澄清、方案约束、客户沟通、验收 | 售前演示 ≠ 生产运维 |
| 范围、资源、跨团队依赖、风险与变更 | 决策事件、本人权限、取舍、交付依据 | 经理头衔 ≠ 管预算或直属人员 |

“算法工程师”可能有不同工作。职责混合则标出各部分，比例未知就问。借鉴 [OPM 岗位分析](https://www.opm.gov/policy-data-oversight/assessment-and-selection/job-analysis/)的任务—能力关系；下面刻度与分档是 career 规则，不是 OPM 标准。

## 2. 条件不能用平均分抵消

单列用户不可妥协条件、JD 明确必要条件：条件、依据、满足／不满足／未知、能否协商。不把“优先”升为门槛，不按年龄、性别等属性自行打分。年限、证书与范围据实核对。

- 确认硬冲突：先处理冲突，不因薪资高就推荐立即投入。
- 关键条件未知：先核实；可协商但尚未确认仍是未知，不替用户放宽底线。
- 条件满足：再比较可权衡项。已作为门槛的城市等事项不重复加减分。

## 3. 两张表分别评价

**能力匹配**回答“证据支持完成哪些任务”。可按核心交付、质量验证、协作推进、业务情景分组；不相关组删去并说明。每组先写该岗位合格行为，再列关键要求。确认没有经验可以低分；材料没有提到用未知。

| 值 | 能力证据锚点 |
| --- | --- |
| 0 | 已明确不具备该必要经验／能力，或实际案例与要求相冲突 |
| 1 | 有邻近知识或尝试，尚不能支持所需交付 |
| 2 | 有部分实际交付；自主程度、复杂度或情景低于此岗位要求 |
| 3 | 能说明本人完成同等任务的过程、判断与验证，符合岗位期望 |
| 4 | 在更复杂或多个情景下有可迁移的具体证据，能解释边界与取舍 |
| U | 未问清、矛盾或不足以判断，不是 0，也不能默认 2 |

一次经历完整满足目标要求也可以是 3；不靠年数、品牌、项目数或工具名升到 4。每个数值关联事实 ID＋章节和锚点解释；可迁移经验写明相同点、差异。

**机会价值**回答“符合用户想要的下一步吗”。从[公司研究](company-research.md)选用户关心且相对独立的维度，如工作与成长、团队资源、业务持续性、保障回报、生活安排。不要再加入“公司总分”重复计算。

刻度：0 明确与此项偏好相反；1 明显低于期望；2 可接受但有具体代价；3 达到用户期望；4 有证据支持超出期望；U 未知。每维度补具体锚点，例如“成长 3＝明确负责模块且有可验证的指导安排”，不是“成长很好”。偏好未了解时给条件式比较，不算貌似个性化的价值分。

## 4. 权重与缺失信息

先定口径，再看谁排名高。每张表权重合计 100；子项分本组权重，不让条目多的组占优。有明确偏好／任务依据则据此确定；否则**临时等权，说明未校准**。比较机会时价值表用同一目标与刻度；不同岗位能力分仅表示各自适配，不能当跨岗位能力高低。

用“此项从最差到最好会多大程度改变选择”检验权重，不只问“重要吗”。不能互相补偿的条件移到门槛。合并相关项，例如薪资、年收入、现金回报不能算三次。借鉴[多准则决策](https://analysisfunction.civilservice.gov.uk/policy-store/an-introductory-guide-to-mcda/)的取舍与敏感性思路；这里是简化启发式，不宣称完整实施或验证了 MCDA。

权重 w、分数 s（0–4）、已知项集合 K：

```text
覆盖 C = ΣK w / Σ全部 w × 100
已知项得分 S = ΣK(w × s) / (4 × ΣK w) × 100
未知取最低的边界 L = ΣK(w × s) / (4 × Σ全部 w) × 100
未知取最高的边界 H = L + (100 − C)
```

全未知时 S=null，C=0，边界 0–100。边界是缺失项取极值时的范围，**不是置信区间**；已知项也可能有误。不能只显示 S 而隐去 C；覆盖不能冒充证据可靠性。弱来源、过期或冲突仍需核实。

可用[计算辅助脚本](../scripts/score-opportunity.mjs)复核数学，它不判断材料、不生成推荐、不写卡片。输入及演算见[案例](worked-example.md)。无 Node 的桌面工作区按上式复核，不要求额外安装环境。

## 5. 如何推荐

默认先给理由和下一步。如需写 card 的 recommendation，按下表从上到下判断，与 user_rating 完全分开：

| 情况 | 建议／recommendation.rating |
| --- | --- |
| 确认的不可妥协冲突 | 1：当前条件不适合，说明能否重谈，不自动结束岗位 |
| 关键未知／冲突证据、用户目标未明确，或任一表 C < 80 | 暂不评级：recommendation 为 null，先核实，不用 3 星掩盖未知 |
| 任一已确认核心能力 < 2 | 2：当前差距较大，说明差距与补足路径 |
| S能力 < 50 或 S价值 < 40 | 2：较低优先级，给具体原因 |
| S能力 ≥ 75 且 S价值 ≥ 75，权重变化后主要结论仍成立 | 5：优先了解／准备，不是自动投递或保证录用 |
| S能力 ≥ 65 且 S价值 ≥ 60 | 4：值得推进，说明代价与补充项 |
| 其余有充分依据的情况 | 3：取决于用户愿意作何取舍 |

这是 v1 默认政策，不是行业公认阈值。74 与 75 等边界附近不要断言质变。证据或权重变化后重评并保留理由，不为预期评级倒调权重。

比较接近机会时，把最重要维度权重上下调 10 个百分点，其余按比例缩放，观察排序或分档；至少比较用户实际关心的两种侧重。轻微变化就逆转则报告“取决于偏好”。单项或权重边界处使用可行范围，说明未做的变化。

## 6. 保存以便复查

analysis/match.md 保留目标、资料日期、岗位类型、硬条件、要求—证据—锚点—权重、两张表结果及未知、敏感性、建议与改变结论的条件。完整表仅在评分时需要，正文自由组织。

recommendation 仅支持 rating（1–5）、reason、evidence、assessed_at。矩阵放文档，不塞未支持字段；依据失效时清空旧评级并留原因。写回按[CLI](cli.md)，不修改用户星级、阶段或实际投递状态。
