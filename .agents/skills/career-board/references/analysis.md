# 公司、岗位与推荐：先判断问题，再选方法

这不是工具使用清单。先读岗位 context、JD、用户意向和相关事实，确定本次要回答的决定：值得继续了解、需要补什么证据、怎样准备，还是比较几个机会。已有信息直接复用，不把用户拉回问卷。

| 当前任务 | 必读方法 | 产物 |
| --- | --- | --- |
| 公司怎么样、哪些地方需要核实 | [公司研究](company-research.md) | analysis/company.md：事实、解释、对用户的影响、反证与下一问 |
| 能否胜任、怎样评分和推荐 | [岗位评价与评分](job-evaluation.md) | analysis/match.md：任务证据、条件、分数依据、未知及建议 |
| 查询主体或工商资料 | [企查查操作](company.md)，结合研究问题 | 查询证据及主体确认，不把回执当分析 |
| 面试准备、考核和模拟 | [面试协作](interview.md)、[考核设计与评价](interview-assessment.md) | 按轮准备与独立模拟，不改变真实结果 |

完整演算和判断见[虚构案例](worked-example.md)。不是每次都要打分，也不是有一个好分数就能跳过判断。

公司分析写 `analysis/company.md`，岗位匹配写 `analysis/match.md`。先读取原文和摘要，再增量写入；正文自由组织，以下是判断方法，不是必须填满的页面字段。命令与并发保护按 [CLI](cli.md)，企查查按 [企业查询](company.md)。

## 公司：先回答与这个机会有关的问题

先确认招聘品牌、具体团队和用工主体是否一致；不明时注明。依据用户关注点选择业务稳定性、团队与岗位、发展空间、工作条件等问题，避免堆砌工商百科。

- 官网、正式披露和岗位原文适合判断业务与公开承诺；企查查支持工商主体等查询。引用实际取得的页面／数据、日期及对应结论。
- 招聘方表述是对方说法；用户面试反馈是该次交流的观察。论坛、社交媒体评价要标明匿名性、时间、样本和主体是否匹配；个案不能直接推广成整家公司结论。
- 相互矛盾的材料并列保留，说明需验证什么。没有查到信息不等于没有风险，工商正常不等于工作氛围良好。
- 把关键未知转成可问招聘方的问题，例如团队归属、汇报对象、岗位新增还是替补、交付预期。不要自动发送。

交付时能看出“已知什么、依据在哪里、这对用户意味着什么、还需核实什么”。用户仅要求主体查询时交付查询结果，不自行扩展成全面调查。

## 匹配：重要要求与已有事实相对照

1. 从 JD 区分核心职责、明确硬条件、优先项和工作条件。未写明的要求不要自行补成门槛。
2. 对每个决定性的要求，定位到用户实际事实／母版／简历中的具体依据；分别标注有证据、部分支持、材料未体现、明确不满足。未体现不等于没有能力。
3. 若一处未知可能改变选择，优先问这一处。例如“有跨部门推进经验”先找实际事件，不因职位名相近就判断满足。
4. 结合用户已明确的意向解释机会与代价。给出当前建议、依据和不确定性；不凭关键词数量生成精确匹配率、录用概率或替用户打星。
5. 推荐调整表达时链接真实经历，缺能力不能通过改词创造。需要定制简历再交给 [resume-tailor](../../resume-tailor/SKILL.md)，保留原包与岗位关联。

材料不足时给出限定范围的初步判断，保留最有价值的下一问。实际分析写回后再完成相关待办；原文、分析、用户决定分别保留。准备投递、已经投递、是否放弃由用户实际决定或事实推进，不由分析结论自动改变。
