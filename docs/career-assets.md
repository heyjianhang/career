# 职业资产的记录与写作

职业资产是有来源、能继续追问的完整经历记录。它服务于简历、面试、能力盘点、职业选择，也可以为后续业务与项目规划提供案例。当前工作只整理真实经验，不因为存在这些用途就替用户启动规划任务。

## 一份事实，多种用途

| 层次 | 保存内容 | 谁负责 |
| --- | --- | --- |
| 原材料 | 文档、图片、作品、口述及其时间与原文位置 | career-intake 登记来源 |
| 详细资产 | 任职范围、项目全貌、角色、关键事件、过程、决策依据、交付、局限与复盘 | career-employment / career-project |
| 可复用表达 | 从详细事实选出有依据的表达与多个可用侧面 | resume-master |
| 具体用途 | 针对岗位、篇幅、平台和面试问题选材 | resume-tailor / career-board |

资产继续保存在 `resume/facts/`，沿用 v2 数据契约与稳定 ID；不另建一份“资产库”复制事实，也不让用户为新能力迁移旧目录。普通正文可以细写，YAML 保持现有字段。模板是起步骨架，不能据此限制用户的叙述深度。

## 先留下地图，再深入一处

接到大量材料，先保存来源，识别单位、任职阶段、项目及工作线。记录“已知但尚未展开”的线索。对重要或复杂经历，由实际范围决定要谈哪些阶段、工作线与关键事件；没有固定题数、字数或案例数量。一个案例问清楚不等于整段经历问完。

每次围绕用户刚提到的一个具体事实继续：先理解发生了什么，再问其角色与选择，最后追到实际结果。不要把维度表一次发给用户填。用户回忆不清时，可以从文档、时间节点或一次具体场景唤起记忆；没有证据就保留未知，不替用户补情节。

## 关键事件如何留下来

在对应项目或任职正文中，用有意义的三级标题组织事件，例如“试点前发现权限边界不一致”。按实际发生的内容叙述：

- 当时的触发、参与角色和已有条件；为何值得处理。
- 本人接到什么责任，能决定什么，谁参与、谁最终决定。
- 有哪些实际考虑过的选择，各自约束是什么；不要事后虚构备选方案。
- 本人具体做了什么、先后顺序、与其他人的分工、遇到的变化或返工。
- 交付和使用到什么阶段，怎样核对结果，依据在哪里；团队成绩与个人动作分别写。
- 后来如何看这件事，有哪些尚未解决的限制；“下次可能这样做”属于复盘设想，不能写成已实施动作。

简单执行任务也可以按真实过程记录，不强求重大冲突。管理、业务、研究、设计与工程采用相同的真实性标准，不套固定技术栈。失败、终止、未采纳方案、协作困难也有资产价值，不能为了让简历显得成功而从事实层删除。

## 写法：详细而可检索

第一段先讲清这是什么、服务谁、处于什么时期和阶段。随后按工作线／时间节点组织，段落有明确主语、对象与动作，保留解释因果所需的上下文。长材料可以拆出可定位的段落与附件引用，不用一整段流水账，也不压成三条简历短句。

正文区分四种东西：已发生的事实、用户本人的复盘看法、Agent 根据材料形成的待核对理解、尚未取得的信息。后两者不能混入确定事实。用户口述是来源，不等于已经外部证实；公开网页只能支持其中明确写到的内容。

证据不只是一串 source ID：重要数字、归属和关键决策在相应段落旁写明来源位置（访谈日期／问题、文档章节或页码）。数字保留单位、时段、统计范围；允许用户提供带依据的近似值，并明确标注近似及依据，禁止 Agent 为填空猜测。

保留用户已经给出的专业细节，必要时解释术语；删去没有信息的夸饰。不能把“参加评审”改成“负责架构决策”，不能把“接入模型”改成“训练模型”，不能从截图推定上线规模。附件原件可留在 sources，正文解释附件能证明什么、不能证明什么。

内部资料仅用于理解与核对；公开链接、客户名及敏感细节是否对外展示，在成品选材时按用户选择处理，不默认暴露。资产层记录与展示层取舍分开，去标识后的表达也不能改变事实。

## 回读时用接手者视角

另一位 Agent 能否根据这份正文解释当时为何做、本人负责哪里、怎样推进、实际交付与结果是什么，并找到依据和下一处未知？若仍需重新问“这个项目到底是做什么的”“你究竟做了什么”，就继续整理。校验通过只能说明格式合法。

给用户看一段具有代表性的整理，以及仍待补的内容，允许其纠正误解；不是要求每一行审批。根据实际证据判断“本轮已整理”，未答复的关键归属仍留待补充。转段规则见 [引导与推进](agent-workflow.md)。

## 从资产到简历的虚构示例

以下仅用于说明写法，不能复制为真实用户经历。

**过浅**：“负责知识库项目，推动上线，提升效率。”

**资产片段**：“售后同事原先按文件夹寻找不同版本的手册。该项目先覆盖一个试点团队。本人负责需求整理、试点计划和验收清单；检索实现由工程同事负责，访问策略由信息安全负责人批准。试点前，同一份材料在不同角色下可见范围不一致。本人收集两类使用角色的实际查询场景，与工程同事逐条核对，补充了无权限材料不得展示的验收情形。原计划的跨团队试用因此延后，先在试点团队复核再决定扩大范围。现有记录只支持完成试点验收，尚无全面上线或节省工时的统计。来源：虚构访谈中的试点与分工叙述；验收清单尚未提供，已登记待补。用户复盘认为，权限场景应该更早进入需求检查。”

**母版可提炼**：“负责知识库试点的需求整理、计划与验收；协同工程和安全负责人核对访问边界，补充角色权限验收场景并完成试点验收。”

短句只选用了其中一部分。原来谁决策、怎样处理变化、尚未上线和复盘想法仍留在资产中，后续面试或项目复盘可以重新取用。
